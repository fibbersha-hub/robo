# MetalsGridConfluence v4.20 — пакет для независимого аудита

## Статус

Это **review-кандидат**, собранный на основе загруженного оригинала `MetalsGridConfluence_v4.mq4` версии 3.10. Он предназначен для чтения, компиляции и анализа другим экспертом. Это не сертифицированный и не проверенный на реальном брокере релиз.

Оригинальный файл не изменялся. Рабочий советник на домашнем сервере не затрагивался.

## Что добавлено

- Отдельный режим HEDGE/RECOVERY по каждому символу.
- Состояния OFF / WATCH / ACTIVE. WATCH начинается при 15%, ACTIVE — при 20%; выход реализован с гистерезисом 2 п.п.
- Выбор знаменателя для порогов: `HedgeDDBase=HEDGE_DD_ACCOUNT_BALANCE` по умолчанию либо `HEDGE_DD_RISK_BUDGET`.
- Базовый знаменатель фиксируется на начало WATCH/ACTIVE-эпизода.
- Сигнал построен по закрытым H4-барам: EMA + RSI. Для открытия дополнительно нужен брокерский tick volume выше среднего за предыдущие 20 баров на коэффициент 1.20. Объём тиков используется только для входа, не для выхода.
- По умолчанию подтверждение входа — 2 закрытых H4-бара; выход — 2 закрытых H4-бара без подтверждения EMA/RSI.
- Отдельный magic для хеджей: `MagicBase + 50 + symbolIndex`; проверка ограничивает `MaxSymbols` значением 50.
- Размер хеджа ограничен долей исходной корзины: от 25% при активации до максимум 75% при `HedgeFullLossPct`; нетто-направление не должно переворачиваться.
- Прибыль хеджей реализуется по отдельным прибыльным ногам; 70% чистой реализованной прибыли зачисляется в recovery pool, 30% остаётся резервом.
- Recovery pool может быть отрицательным: дефицит от убытков не обнуляется, а переносится и сначала покрывается последующими прибылями.
- Pool закрывает наиболее убыточные ноги исходной корзины частично или полностью.
- Добавлен жёсткий стоп плавающего убытка хедж-корзины: 1% выбранной базы; повторные чисто убыточные закрытия корзины/срезания хеджа учитываются в stop counter. После двух таких событий новые хедж-входы блокируются до выхода из эпизода.
- При наличии открытой хедж-корзины блокируются grid-adds, штатное MRP-закрытие и MRP-сокращение исходной корзины. Basket TP и Kill Switch продолжают закрывать обе корзины.
- Исправлена дедупликация журналов: независимые слоты для stats/open/MRP-hold/close.
- Учтён результат штатного MRP partial reduction, если он происходит во время WATCH.
- Закрытие и учёт P/L хеджей выполняются по каждому тикету, чтобы не терять уже реализованный результат при частично неудачном закрытии корзины.
- Исправлена проверка закрытых ордеров: при `OrderSelect(..., SELECT_BY_TICKET)` параметр pool игнорируется; теперь статус закрытия проверяется по `OrderCloseTime()`.
- Kill Switch и orphan cleanup учитывают hedge magic.

## Важные значения по умолчанию

| Параметр | Значение | Смысл |
|---|---:|---|
| `HedgeShadowMode` | `true` | Хедж-ордера не открываются; режим только логирует потенциальные действия |
| `HedgeDDBase` | `HEDGE_DD_ACCOUNT_BALANCE` | Порог считается от баланса счёта |
| `HedgeWatchPct` / `HedgeActivePct` | 15% / 20% | Пороги на каждый инструмент отдельно |
| `HedgeHysteresisPct` | 2 п.п. | Гистерезис |
| `HedgeFullLossPct` | 40% | При этой просадке достигается максимальная доля хеджа |
| `HedgeMinRatio` / `HedgeMaxRatio` | 25% / 75% | Целевой диапазон хеджа к исходным лотам |
| `HedgeLegRatio` / `HedgeMaxLegs` | 25% / 3 | Размер одной ноги и максимум одновременно открытых ног |
| `HedgeMaxLossPct` | 1% | Hard stop по плавающему убытку хедж-корзины от выбранной базы |
| `HedgeMaxStopCount` | 2 | Лимит чисто убыточных закрытий/срезаний хедж-корзины на эпизод |
| `HedgeProfitUsePct` | 70% | Доля чистой прибыли хеджа, доступная для компенсации |
| `HedgeLegMinProfit` | 5 | Минимальная чистая прибыль одной ноги для её фиксации, в валюте депозита |

### Пример порогов

При балансе 10 000 и настройке `HedgeDDBase=HEDGE_DD_ACCOUNT_BALANCE` WATCH соответствует убытку инструмента 1 500, ACTIVE — 2 000.

При выборе `HEDGE_DD_RISK_BUDGET` знаменателем становится результат существующей функции `GetRiskBudget()`. Например, при балансе 10 000, `MaxRiskPercent=40` и `RiskBalanceCap=20 000` бюджет равен 4 000, поэтому WATCH — 600, ACTIVE — 800.

Числитель — нетто-убыток эпизода конкретного символа: текущий floating P/L исходной корзины + floating P/L хедж-корзины + записанный реализованный результат хеджа/компенсаций. Это не глобальная просадка счёта и не ATR stress-risk.

## Режим Shadow — важное уточнение

`HedgeShadowMode=true` отключает только торговые действия нового HEDGE/RECOVERY слоя. Основная стратегия v3.10 продолжает работать как прежде, включая её штатные входы, сетку и MRP-защиту. Это не общий режим paper trading. Для полного запрета торговли у советника есть исходный `LogOnly`.

Если `LogOnly=true` при уже существующих хедж-ордерах, советник не сможет их закрыть и будет блокировать новые входы по символу до устранения ситуации. Не переключать `LogOnly` на живом хедже без ручного контроля.

## Что обязательно проверить второму эксперту

1. Открыть файл в MetaEditor текущей сборки MT4, скомпилировать и предоставить полный список ошибок/предупреждений. В этой среде MetaEditor/MQL4 compiler не обнаружен, поэтому компиляция здесь **не подтверждена**.
2. Проверить на тестовом счёте семантику частичного закрытия в конкретном MT4-брокере: что возвращается в history, меняются ли ticket IDs, как распределяются комиссия и swap. В коде предусмотрен fallback на оценку до закрытия, если history P/L ещё недоступен; такие случаи должны отмечаться как `estimate`.
3. Проверить реальные ограничения брокерского счёта: разрешены ли встречные позиции, FIFO/netting, hedge margin, минимальный лот и шаг лота по XAU/XAG.
4. Проверить сценарии: OFF→WATCH без новых hedge orders; WATCH→ACTIVE; вход только после подтверждённых закрытых H4-баров и объёма; выход по EMA/RSI, а не по падению объёма; hard stop; stop-counter lockout; использование recovery pool; orphan cleanup; Kill Switch при открытых исходной и hedge-корзинах.
5. Отдельно перепроверить знаменатель 15%/20% и то, что ожидается именно нетто-убыток эпизода, а не только текущий плавающий убыток исходной корзины.
6. Проверить, не требуется ли учитывать hedge exposure в стороннем watchdog или внешней системе мониторинга: встроенный stress-risk намеренно считает исходную корзину, а hedge orders проходят отдельную проверку маржи.
7. Запустить сначала на демо/Strategy Tester с `HedgeShadowMode=true`, изучить status/events и сверить все расчёты. Реальный торговый режим не включать до завершения аудита.

## Известные ограничения

- Тиковый объём по металлам — данные конкретного брокера, а не централизованный объём всего рынка.
- Hedge TP и hard stop используют цены и P/L брокера; спред, комиссия, swap и проскальзывание могут изменить фактический результат.
- Если брокер не предоставляет закрытый тикет в истории сразу после сделки, в recovery ledger записывается оценка по данным до закрытия и выводится соответствующее сообщение.
- Отсутствие доступной H4-истории не формирует новый сигнал на открытие. Существующий хедж не закрывается автоматически только из-за отсутствия индикаторных данных.
- Код не был скомпилирован MetaEditor и не прошёл Strategy Tester на данных/спецификации вашего брокера.
